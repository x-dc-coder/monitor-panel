## B. 技术选型

| 决策 | 评审 | 结论 |
|---|---|---|
| FastAPI 单服务 + uvicorn 单 worker | ✅ 论证成立：采集为 I/O 密集，asyncio 单进程足够；单 worker 避免采集重复执行 + SQLite 写竞争 + 内存快照不一致。补充两点：① 所有 collector 必须 async + 每步强制 timeout；② psutil 磁盘扫描等同步调用若 >50ms 建议 `asyncio.to_thread`，防 API 延迟抖动（单 worker 下任何阻塞都会拖慢全部请求） | 通过 |
| 自研 asyncio 调度器 vs APScheduler | ✅ 合理：全部是"间隔执行"语义，无需 cron 表达式；~50 行成本可控。补充：需处理周期超时跳过（overrun 不追跑）、调度抖动（加 jitter 防齐射）、用单调时钟 | 通过 |
| Chart.js vendored | ✅ 200KB 本地化，出站异常时面板仍可用；不沿用 echarts 是刻意取舍（轻量优先），接受。补：附带 MIT LICENSE 文件 | 通过 |
| 轮询 vs SSE/WS | ✅ 5–10s 轮询匹配 30s 采集节奏，免 nginx 长连接特殊配置；SSE 列为可选增强判断正确 | 通过 |
| SQLite WAL + 30 天保留 | ✅ 估算 5.8 万行/天、30 天 ≈170 万行带索引无压力（t1 A7.2 实测 8899 库 3.7MB/3.7 万行佐证量级）；每小时 DELETE + `wal_checkpoint(TRUNCATE)` 低频低竞争。补充：设计未写 `PRAGMA busy_timeout`、`synchronous=NORMAL`，应补上 | 通过 |

**一处事实性错误（需修）**：F1 写 `GET /api/proxy/all`，但 t1 B5 实测 frp 0.70 dashboard 为 **per-type 端点**（`/api/proxy/tcp|udp|http|https|stcp|xtcp`），`/api/proxy/all` 是否存在**未验证**。应按 t1 实测实现（先探测 `/api/proxy/all`，不存在则聚合 per-type），并保留降级（dashboard 不可用 → 只用 8899 agent 数据）。

## C. 安全与运维纪律

### C1. certbot HTTP-01 vs DNS-01 —— 🔴 阻塞级风险（本次评审最关键项）

**冲突事实**：
- 队长给架构师的 t2 指令原文明确要求"certbot 签发 monitor.dc-sy.cn 证书（**参考 headscale 的 DNS-01 经验**）"——即团队已知 headscale 曾因**腾讯云 webblock 拦截 HTTP-01** 而走 DNS-01。
- 架构师方案 §2.5/§6 却改选 **HTTP-01 为唯一签发方式**，并断言"headscale 实际也是 HTTP-01，不需要 DNS-01"——**与队长指令直接矛盾，且未提供验证依据**。

**技术评估**：腾讯云对**未 ICP 备案域名**在 80 端口投放 webblock 拦截页，ACME HTTP-01 挑战请求会被拦截页劫持 → 签发失败。同服务器、同域名体系（dc-sy.cn 子域）下的 monitor.dc-sy.cn **完全可能同样被拦**。t1 报告"headscale 也是 HTTP-01"与"曾被拦"并不矛盾（可能备案补齐后成功，也可能 t1 只看了 nginx 配置残留的 acme-challenge location 未实测签发），但**对 monitor.dc-sy.cn 该假设未经验证，不能默认成立**。若被拦，M4 签发失败 → 上线阻塞，且此问题只能在部署期暴露、无法本地预演。

**要求（修改点 1，阻塞）**：
1. 部署步骤 8 前插入**预检 8a**：DNS 生效后从外部网络执行 `curl -sI http://monitor.dc-sy.cn`，检查返回 200/301 正常重定向还是腾讯云 webblock 拦截（`Location: https://webblock.tencentyun.com/...` 或 qcloud 拦截页）；同时向用户确认 dc-sy.cn 是否已 ICP 备案（已备案则 HTTP-01 基本可通行）。
2. `setup_nginx_cert.sh` 支持**双通道签发**：`--issuance http|dns` 参数。HTTP-01 走 certbot `--nginx`；DNS-01 走 acme.sh `dns_tencent`/`dns_dp`（DNSPod API token，需预先申请，注意 Tencent DNS 的 token 权限只需要"解析记录"读写即可）。DNS-01 无需 80 端口入站，完全绕开 webblock。
3. **续期必须与签发方式一致**：若走 DNS-01，续期 hook 同样要配 DNSPod 凭据（acme.sh 自动续期天然支持；certbot manual hook 需 deploy-hook 持久化），否则 90 天后续期失败。
4. 上线 checklist 增加一行："HTTP-01 预检通过 或 已用 DNS-01 签发"。

### C2. 8898 绑 127.0.0.1 + nginx 反代

✅ 得当。备选 8900 合理。建议 **nginx 层 Basic Auth 默认开启**（个人面板防扫描，成本一行），设计目前是"可选"，应改为"默认开、可关"。

### C3. 与 8899 并列共存 + 只读消费

✅ 正确：不动生产（采集端契约是不可变基线，t1 A8.3 认同）、双源对照（frps dashboard 权威 + 8899 agent 补充，任一挂掉仍有另一半数据）、未来 `ingest.py` 同构迁移路径清晰。注意消费 8899 `/api/status` 需其 API_TOKEN 存入新面板 config → 落盘保护见 E6。

### C4. systemd / 原子切换 / 回滚

✅ releases/current 符号链接 + deploy.sh 健康检查回滚段设计合理；`Restart=on-failure` 应补 `StartLimitIntervalSec` 防重启风暴；回滚"schema 向前兼容"论断成立（samples 追加式）。日志双份（journald + 文件）需配 logrotate，见 D4。

### C5. 数据源命令 root 权限处理（队长点名项）

设计 R2 采用"服务以 root 运行（与 8899 一致）"——**可行但非最佳**：面板是经 nginx 暴露的 Web 服务，root 运行把 Web 攻破面放大到整机（8899 是历史包袱，新服务不应复制该模式）。两个方向：

1. **推荐**：专用用户 `monitor` + **sudoers NOPASSWD 白名单**仅放行 3 条只读命令：
   - `tailscale status --json`
   - `tailscale ping <ip>`
   - `headscale nodes list -o json`
   证书目录 `/etc/letsencrypt/live/*` 只读放行。sudoers 条目形如 `monitor ALL=(root) NOPASSWD: /usr/bin/tailscale status --json, /usr/bin/tailscale ping *, /usr/bin/headscale nodes list -o json`（注意 tailscale ping 参数校验，防注入）。
2. 若坚持 root（开发期最快）：须在 README 记录权衡，并排期 M5 收敛为白名单。

权限连带影响（选非 root 时注意）：F7 的 ICMP ping 需 `cap_net_raw` 或 setuid ping；tailscale CLI 访问 `/var/run/tailscale/tailscaled.sock` 的 socket 权限；headscale CLI 读 `/var/lib/headscale` 配置。sudoers 白名单方案下这些都由 sudo 规避。

## F. 修改点汇总（交付 architect）

**🔴 阻塞（M4 前必须闭环）**：
1. **证书签发策略改双通道**：新增部署步骤 8a（外部 `curl -sI http://monitor.dc-sy.cn` 查 webblock + 向用户确认 dc-sy.cn 备案状态）；`setup_nginx_cert.sh` 支持 `--issuance http|dns`；DNS-01 用 acme.sh `dns_tencent`/`dns_dp`（DNSPod token 预先申请），**续期 hook 与签发方式一致**。

**🟠 必须修正（M2/M3 内）**：
2. F1 数据端点改为 t1 实测 per-type（`/api/proxy/tcp|udp|http|https|stcp|xtcp`），先探测 `/api/proxy/all` 存在性二选一，保留降级。
3. F1 补充消费 8899 `/api/status` 的 `latency_ms / packet_loss_percent`（frp 链路质量维度），并入 samples。
4. collectors 增加统一脱敏层（公钥/密钥指纹过滤）与敏感配置 env 注入 + 600 权限。
5. ping 超时语义明确（在线+超时=warn 防抖，离线=展示不告警）+ 子进程 kill + `asyncio.Semaphore` 限并发；手动 ping 限流。
6. 权限模型决策：**monitor 用户 + sudoers 白名单（3 条只读命令）为推荐**，root 为临时妥协并排期收敛；写明 ICMP 权限依赖。
7. SQLite 补 `busy_timeout` / `synchronous=NORMAL`；调度器补 overrun 跳过与 jitter。

**运维步骤补齐（M4 checklist）**：D1 安全组确认、D3 nginx/letsencrypt 快照、D4 日志轮转、D5 每日 db 备份（D2 已并入阻塞项）。

**排期建议**：8899 加固（绑 127.0.0.1 + Basic Auth + token 改 header）列入 M5 前置任务，需用户审批（改动面 = 8899 systemd 启动参数 + nginx，与采集端契约无影响，风险低）；E10 ingest 可达性并入 M5 cloud-2 任务定义。

## 2. DNS-01 插件事实修正核验（队长点名项）——**修正成立 ✅**

架构师实测 **dc-sy.cn NS = dns31/32.hichina.com（阿里云万网 DNS）**，据此将 DNS-01 通道由我原建议的 `dns_tencent/dns_dp` 改为 **acme.sh `dns_ali` + 阿里云 RAM AK（Ali_Key/Ali_Secret，仅授权 DNS 解析记录读写）**，并保留 certbot-dns-aliyun 为备选。**判断：修正正确，接受。**

- 原理：DNS-01 的 TXT 记录（`_acme-challenge.monitor.dc-sy.cn`）必须写入**权威 NS 所在平台**（阿里云 DNS 控制台/API）。域名 NS 不在腾讯云/DNSPod 时，dns_tencent/dns_dp 插件无法操作该 zone——**确实不适用**（除非子域单独 NS 委托，复杂度高不划算）。
- `dns_ali` 插件的环境变量即 `Ali_Key`/`Ali_Secret`，与 headscale 既有"阿里云 AK 走 DNS-01"经验一致，可复用。
- 自我修正：我原建议基于"腾讯云服务器 → 腾讯云 DNS"的想当然假设，**未核实 NS 记录，属评审瑕疵**；架构师以实测数据纠正，本次复审确认采纳。
- 遗留确认项（非阻塞，方案已覆盖或属用户侧）：①RAM 子账号权限收敛（AliyunDNSFullAccess 或更小自定义 alidns:Describe/Add/DeleteDomainRecord 策略）；②acme.sh 凭据文件 600 + 不入 git（§6 步骤 9 已含）；③Ali_Key 归属账号须能管理 dc-sy.cn 解析（用户侧确认，已列入前置）。

| # | 问题 | 严重度 | 说明与建议 |
|---|---|---|---|
| N1 | **Basic Auth 默认开 × HTTP-01 通道冲突** | 🟠 中（仅影响 http 通道；走 dns 通道则无关） | v1.1 同时落地"Basic Auth 默认开启"与"HTTP-01 签发"，但 certbot 的 ACME 挑战请求**不带凭据**：若 `auth_basic` 作用域覆盖 `/.well-known/acme-challenge/`，Let's Encrypt 校验将 401 失败（签发与续期都会失败）。**一行补充修正**：monitor server block 增加 `location ^~ /.well-known/acme-challenge/ { auth_basic off; }`（或该目录置于 auth 作用域之外）；预检 8a 的判定应把 **401/403 视为"Basic Auth 干扰，先补豁免再判"**，而非误判为通过。走 dns 通道时不受影响，但仍建议保留豁免为将来 http 迁移留路 |
