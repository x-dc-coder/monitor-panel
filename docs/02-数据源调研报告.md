字段说明与采集要点：

- `LastSeen`：**在线时是 Go 零值 `0001-01-01T00:00:00Z`**（解析时必须判 Online 优先）
- `RxBytes/TxBytes`：直连流量计数；当前全中继所以为 0（中继流量计在 DERP 侧）
- 需 root；输出约几 KB，含节点公钥指纹，**落库需脱敏**

### B3. tailscale ping（`sudo tailscale ping <IP>`，已实测）


## C. 多云服务器兜底 / 双公网 IP 调研结论

### C1. tailscale 多 exit node —— ✅ 支持

- 任何节点 `tailscale up --advertise-exit-node` 即可成为出口节点，客户端用 `--exit-node=<IP>`（或域名）按需切换；headscale 控制面同样支持（路由需在 headscale 侧批准，`headscale routes` / ACL）
- Tailscale 官方还有 **Auto Exit Nodes**（按延迟/策略推荐出口），更易用
- 结论：**第二台云服务器可注册为第二个 exit node**，设备在"主出口/备用出口"间一键/自动切换，实现出站链路的双公网 IP 冗余
- 来源：[Tailscale Exit nodes 文档](https://tailscale.com/docs/features/exit-nodes)、[Auto Exit Nodes 博客](https://tailscale.com/blog/auto-exit-nodes)、[headscale Exit node 文档](http://headscale.net/0.23.0/ref/exit-node/)、[headscale Routes/Exit Nodes](https://raw.githubusercontent.com/juanfont/headscale/main/docs/ref/routes.md)

### C2. headscale 多 DERP —— ✅ 支持

- config.yaml 支持 `derp.urls`（外部 DERP map 列表）+ `derp.paths`（自定义 map 文件），内嵌 DERP（当前 region 999）自动并入；region id 冲突时本地优先
- 结论：**第二台服务器可再部署一个 headscale 内嵌 DERP（或引用公共 DERP），实现中继层冗余**——当前全部节点走唯一 DERP(headscale)，该服务器若挂，中继链路全断（虽然不影响直连）
- 来源：[headscale DERP 参考](https://headscale.net/development/ref/derp/)、[config-example.yaml](https://github.com/juanfont/headscale/blob/main/config-example.yaml)

### C3. frp 多服务器监控 —— 无现成聚合，需自建拉取

- frps dashboard API / Prometheus 均为**单机粒度**（本地绑定），**没有内置多 server 聚合能力**；官方支持 Prometheus 导出（`webServer.enablePrometheus=true`，当前未开启）
- 结论：多服务器形态 = 每台 frps 暴露本地 admin API/metrics，统一面板做**聚合拉取器**（多 base URL + 循环抓取），自建成本低（十几个请求/分钟）
- 来源：[frp 官方监控文档](https://gofrp.org/zh-cn/docs/features/common/monitor/)、[frp Metrics/Prometheus 集成](https://deepwiki.com/fatedier/frp/7.3-metrics-and-prometheus-integration)

### C4. "第二云服务器作为兜底监控节点"可行路径评估

1. **外部视角探活**（成本最低，强烈建议）：第二台服务器跑轻量采集器，周期探测主服务器公网 IP 可达性 + 8899/9090/7500 端口 + tailscale 跨网 ping → 从独立网络观察主链路，主服务器自己挂了也能告警
2. **加入 tailnet 成为普通节点 + 可选 exit node**：获得第二条公网 IP 直连候选（tailscale 会同时尝试两条路径，CurAddr 可多地址）；配合 C1 实现出口冗余
3. **面板数据源多端配置**：主数据源 health check 失败自动切备用（含前端降级提示），实现监控面板自身的高可用
4. **主备控制面/主备 frps**（二期，复杂度高）：第二台也跑 headscale/frps 形成主备，数据同步与故障切换需专门设计，本次不建议
5. **面板本身不在主服务器单点**：统一面板可部署在第二台服务器，主服务器故障时切 DNS/备用域名

## D. 注意事项与风险

1. **只读纪律**：本次所有远程操作均为只读（GET/status/ping/nodes list/cat），未改任何生产配置；`tailscale ping` 曾因远端命令分类器反复误判，最终经本地 ssh 别名 dc-sy 执行完成
2. **敏感信息**：本报告已打码。完整凭据位置：`/opt/frp-monitor/TOKENS.txt`、`/opt/frp-monitor/server/config.py`（API_TOKEN、POWER_API_TOKEN、SMTP 授权码）、`/etc/frp/frps.toml`（auth.token、dashboard 密码）、`/etc/headscale/config.yaml`（如含密钥）
3. **8899 公网暴露 + URL token**：当前 `0.0.0.0:8899` 公网可直连、token 走 URL 参数（会被日志/浏览器历史记录）。建议统一面板落地时：8899 改绑 127.0.0.1 + nginx 反代 + HTTPS（monitor.dc-sy.cn），header 传 token
4. **frps Prometheus 未开启**：`/metrics` 404。如需 frps 层指标（连接数/流量），需在 frps.toml 加 `webServer.enablePrometheus=true` 并**重启 frps**——影响所有隧道，属需审批的变更，本次未动
5. **headscale metrics 无 per-node 数据**：节点在线/流量必须靠 `nodes list`/`tailscale status`；`LastSeen` 在线时为零值（解析坑）；`RxBytes/TxBytes` 全中继时为 0
6. **权限**：tailscale/headscale CLI 均需 root → 采集器需以 root 运行或 sudoers 白名单单命令；或走 gRPC（需证书）/只读 SQLite（immutable=1）
7. **脱敏**：`tailscale status --json` 含节点公钥/密钥指纹、`nodes list` 含 machine_key/node_key/disco_key，入库/日志前必须过滤
8. **时间格式**：headscale nodes `last_seen` 为 protobuf `{seconds,nanos}`；tailscale `LastSeen` 为 RFC3339；需统一转换为 epoch 存储
9. **生产稳定性红线**：8899 服务与 `/api/report` 契约是 3 台设备 + 树莓派采集端强依赖，整合阶段**不要动它**；新面板以只读聚合方式接入
10. **第二台服务器**：涉及新云资源与防火墙/密钥安全，不在本次调研范围，需单独决策与审批

### A7.1 device_id 的使用方式 —— 唯一的维度键，天然支持多设备

- `reports` 表（实测生产 schema）：

```sql
CREATE TABLE reports (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  device_id TEXT NOT NULL,          -- 唯一维度键，自由字符串，无外键、无设备元数据表
  timestamp REAL NOT NULL,          -- epoch 秒
  latency_ms REAL, packet_loss_percent REAL,
  frpc_alive INTEGER, frps_alive INTEGER,   -- 1/0/NULL 三态（NULL=该设备不适用此字段）
  cpu_percent REAL, mem_percent REAL,
  bandwidth_up_kbps REAL, bandwidth_down_kbps REAL,
  is_startup_sample INTEGER,
  extra_json TEXT                    -- 预留自由字段，当前生产数据均为 NULL（可塞任意 JSON）
);
```

- **设备"档案"不在库里**：`DEVICE_LABELS`（显示名）、`DEVICE_KIND`（always_on/intermittent）、`DEVICE_BANDWIDTH_CAP_MBPS`（带宽上限）、`NO_FRPC_DEVICES` 全部是 **config.py 代码级配置**，靠 device_id 字符串匹配。接入新设备 = 新 device_id + config.py 加一行，**服务端代码和面板零改动**（README 346-348 行明确写了这个扩展方式）。
- **多服务器兜底契合点（已证实）**：`linux_agent.py` 是现成的"新节点模板"——改 `DEVICE_ID`、`SERVER_URL`、`PING_TARGET`、`IS_SERVER=True` 即可把第二台云服务器注册成 `cloud-server-2` 之类，`/api/report` 自动按 device_id 分桶存储，**不需要动 8899 服务**。

### A7.2 历史保留策略

- 保留窗口：`cleanup_old_reports(keep_days=14)`，后台任务每 30s 循环、约每小时清理一次过期行。
- 查询上限：`/api/history/{device_id}?minutes=` 默认 60 分钟、`LIMIT 500` 点。
- 生产实测：共 **36,779 行**（cloud-server 30,329 / desktop 3,941 / laptop 2,509），时间跨度约 **10.6 天**（与 14 天窗口吻合），库文件仅 **3.7MB** —— 体量极小，说明 SQLite 模型完全够用，无需换库。

### A7.3 告警机制

- 触发循环：`background_checker()` 每 30s 调 `alerting.check_and_alert()`。
- 判定逻辑：全部复用 `device_state.classify_device()`（单一真相源，/api/status、cli.py、告警三处共用），含"always_on 离线立即告警 vs intermittent 三态（优雅下线 12h 宽限 / 观望 15min / 意外离线）"、"在线但 frpc/frps 未跑 = degraded 穿透异常"。
- 去重：`alert_log` 表仅用于 30 分钟冷却（按 device_id+alert_type 查最近一次）；实测 33 条告警记录，告警量很小。
- 投递：QQ 邮箱 SMTP（465 SSL），失败静默降级（记日志不重试）。
- 恢复通知：always_on 设备离线告警后恢复上线会补发"已恢复"邮件。

### A7.4 设计意图（README 关键表述）

- "三端监控"→ 设计成"多端"：README 明示"后续接入 Linux 设备：直接复用 linux_agent.py，改 DEVICE_ID…服务端和面板不需要任何改动"——**作者有意把 device_id 做成免注册的设备维度**。
- 健壮性三件套：上报失败 5s/10s 重试最多 3 次、开机抖动标记（is_startup_sample 过滤）、树莓派局域网探测台式机重试 3 次防误判——这些是生产验证过的模式，新面板采集器应沿用。
- 安全模型：电源控制走树莓派主动反向 SSH 隧道（云不主动连内网）、POWER_API_TOKEN 与 API_TOKEN 分离、关机需 confirm 字段、30s 冷却——**新面板若引入任何"控制类"操作必须沿用这套分级授权思路**。

## A8. 整合建议：数据模型"复用 vs 重写"结论

**结论：不重写、不迁移，采用"现有模型原样保留 + 新面板新增快照模型"的混合方案（对应 A6 的并列共存+聚合）。**

| 方案 | 判定 | 理由 |
|---|---|---|
| ① 直接复用现有 reports 表承接一切 | ❌ 不够 | 指标集合固定（延迟/丢包/进程/CPU/内存/带宽），**表达不了** tailscale 连接质量（Relay/CurAddr/直连延迟）、frps 隧道级流量（today_in/out/curConns）、headscale 控制面健康；device_id 维度没有"数据来源类型"字段，无法区分 frp-agent 上报、tailscale 快照、dashboard 拉取三类数据 |
| ② 现有模型不动 + 新面板三类快照表 | ✅ 推荐 | 见下方落地清单 |
| ③ 完全重写统一宽表（time,node,source,metric,value） | ❌ 过度设计 | SQLite 上按 metric 过滤的趋势查询别扭，且与现有设备维度模型脱节，一期收益为负 |

### A8.1 复用清单（直接抄/直接 import）

- **采集端模板**：`linux_agent.py` 的 ping/进程/带宽/开机抖动/重试逻辑 → 第二台云服务器照抄，仅改 DEVICE_ID/URL/PING_TARGET。
- **状态机模式**：`device_state.py` 的 classify 思路（always_on/intermittent 二分 + 优雅下线 + degraded）→ 新面板把 tailscale 节点也纳入"设备"概念（HostName ↔ device_id 映射），**建议把 classify 逻辑抽成纯函数库供两个服务共用**（注意：不要直接 import 现有 config.py/DB 路径，改为参数注入）。
- **告警模式**：`alerting.py` 的 alert_log 冷却 + SMTP 投递 + 恢复通知 → 新面板扩展事件类型（tailscale 节点离线/直连丢失、frps 隧道断开、headscale 控制面 down）。
- **前端模式**：`index.html` 的状态 pill 配色（online/degraded/offline_fault/offline_normal）+ 卡片网格 + ECharts 曲线，语义完全可平移。
- **过渡技巧**：`reports.extra_json` 目前全空，可作为**零改表**的过渡通道——agent 把 tailscale ping 延迟等塞进 extra_json（JSON 字符串），新面板解析展示；结构化落库留给新表。

### A8.2 新面板需新增的数据模型（快照表，落在新面板自己的库，不碰 monitor.db）

| 表 | 关键字段 | 来源 | 频率 |
|---|---|---|---|
| `tailscale_peers` | peer_key, hostname, device_id(映射), os, tailscale_ip, relay, cur_addr, online, last_seen, rx_bytes, tx_bytes, latency_ms(来自 ping), ts | tailscale status --json + ping | 30s / 每节点 30-60s 错峰 |
| `frps_proxies` | server(标识), proxy_name, type, remote_port, status, cur_conns, today_in, today_out, ts | frps dashboard API | 10-15s |
| `headscale_metrics` | 关键 counter/gauge 值（nodestore_nodes、queue_depth、mapresponse 各 type） | 127.0.0.1:9090 | 15-30s |
| `node_meta`（可选） | device_id, source(frp-agent/tailscale/frps-dashboard/headscale), kind, label, server 归属 | 配置 | 静态 |

> 数据一致性要点：旧面板 8899 只读接入（Bearer token 拉 /api/status + /api/history 合并展示历史）；**不要**让新面板直接读写 monitor.db（跨进程 SQLite 写锁风险，且新面板只读 `immutable=1` 打开也只是应急手段）。

### A8.3 给 architect 的落地提示

1. 现有 8899 服务与 `/api/report` 契约是**不可变基线**（3 台设备 + 树莓派采集端依赖），任何整合方案不得要求其改动。
2. 新增设备（第二云服务器）零成本：新 DEVICE_ID + linux_agent.py 复用，可作为一期"多云兜底"的最早落地项。
3. 新面板建议自建独立库与采集器（后台任务或 cron），复用上述四类"模式"而非直接依赖旧代码文件，避免把 8899 的部署路径（/opt/frp-monitor）耦合进新服务。
